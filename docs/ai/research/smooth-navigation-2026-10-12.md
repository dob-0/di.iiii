# Smooth navigation research, 2026-10-12

Scope: why Studio viewport motion (camera-controls 2.10.1, smoothTime 0.15, draggingSmoothTime 0) feels "not smooth" at a measured 60 fps.
Method: camera-controls 2.10.1 source read directly (https://cdn.jsdelivr.net/npm/camera-controls@2.10.1/dist/camera-controls.module.js, fetched 2026-10-12, line numbers below are from that file); docs/pages fetched same day. Items marked UNVERIFIED were not confirmed by a fetched source and must be measured before use.

## 1. camera-controls 2.10.1

- README (https://github.com/yomotsu/camera-controls): smoothTime default 0.25 "Approximate time in seconds to reach the target"; draggingSmoothTime default 0.125 "The smoothTime while dragging"; dollySpeed 1.0; infinityDolly default false ("keeps the distance and pushes the target position instead" past min/max); dollyToCursor default false; update(delta) "returns true if re-rendering is needed"; stop() "stop all transitions"; setOrbitPoint "Set orbit point without moving the camera".
- SmoothDamp (source l.79-100): Unity/GPG4 critically damped spring; omega = 2/smoothTime; velocity state kept per axis. smoothTime is the approximate time to reach target (about 95 % at ~smoothTime*1.5 in practice, UNVERIFIED number). draggingSmoothTime=0 is clamped to 0.0001 s, i.e. the value snaps to the target each frame: no smoothing at all.
  - Could make motion not smooth: with dragging time 0 the camera follows raw mouse deltas 1:1, so any irregularity in event timing goes straight to the screen; and on release nothing is left to ease (no inertia).
- WHEEL USES THE DRAGGING TIME (source l.850 `_isUserControllingDolly = true` in the wheel handler; l.2104 picks draggingSmoothTime while that flag is true; the flag is only cleared by dollyTo/rotateTo etc., l.1445, l.1730, l.1773, not by wheel end; wheel emits no controlstart/controlend, README l.1308).
  - Consequence: with draggingSmoothTime 0 every wheel notch is applied instantly, with no easing. Our smoothTime 0.15 never applies to wheel zoom.
  - Could make motion not smooth: wheel zoom is a staircase of discrete jumps (see next point), not an eased glide. HIGHEST-PRIORITY HYPOTHESIS.
- Wheel step size (l.826-833, 594): delta = deltaY / 30 for deltaMode 0 (deltaY/3 for lines, ctrl-pinch); scale = 0.95^(delta*dollySpeed). A 100 px notch -> delta 3.33 -> radius x 0.843, i.e. 15.7 % of the distance per notch, applied in one frame at draggingSmoothTime 0. UNVERIFIED: Chromium Linux deltaY per notch (commonly 100 in pixel mode; MDN says do not assume, https://developer.mozilla.org/en-US/docs/Web/API/WheelEvent/deltaMode). Measure it.
- dollyToCursor per-notch (l.2137-2175): each frame it moves the target toward the cursor ray by lerpRatio = (prevRadius - radius)/radius, using radius change since last frame. With infinityDolly+dollyToCursor the radius is not clamped (l.595), and at minDistance the camera is pushed along the view direction (l.2155-2160) while spherical.radius is edited directly, bypassing smoothing.
  - Could make motion not smooth: near minDistance 0.35 the path switches branch (clamped dolly vs push-through), a visible speed change/jitter.
- BUG IN LIBRARY (l.812-820): `if (lastScrollTimeStamp - now < 1000) this._getClientRect(...)`: the sign is inverted, the test is always true, so getBoundingClientRect() (forced layout) runs on EVERY wheel event when dollyToCursor is on. Comment says "only need to fire this at scroll start". 
  - Could make motion not smooth: forced layout per wheel event, cost grows with DOM size of the Studio page; shows as long tasks in the Performance panel. Cheap to test.
- stop() (l.1999-2004): NOT a halt. It copies the END values into the current values (`_target.copy(_targetEnd)`, `_spherical.copy(_sphericalEnd)`, focalOffset, zoom). So calling it mid-transition makes the camera JUMP forward to where the spring was heading. Velocities are not reset there (reset only when delta approx 0, l.2084+).
  - Could make motion not smooth: at the start of each gesture, any residual glide (smoothTime 0.15 tail from wheel/pan, or a previous burst) snaps to its destination in one frame: a visible pop at every gesture start and every wheel burst after a 200 ms gap.
- setOrbitPoint (l.1853-1873): doc comment "SHOULD NOT RUN DURING ANIMATIONS. setOrbitPoint() will immediately fix the positions." It calls dollyTo(distance,false), setFocalOffset(...,false), moveTo(...,false): all immediate, no transition. Camera pose should stay identical by design (re-parameterises target/radius/focalOffset), but it overwrites both current and end state, so any in-flight transition is cut (end = current), and it clears _isUserControllingDolly (dollyTo, l.1445) and zeroes _changedDolly.
  - Could make motion not smooth: re-parameterising to a different distance changes what orbit/pan/dolly speed means mid-gesture (rotate speed in camera-controls is by screen height not distance, but pan and dolly-to-cursor depend on radius), so speed can step between bursts.
- Known issues: yomotsu/camera-controls #424 (https://github.com/yomotsu/camera-controls/issues/424, opened 2023-06-06, still open): after setOrbitPoint, dollyToCursor stops working; maintainer: "focalOffset which is used in setOrbitPoint causes many other problems", no plan to fix, suggests removing setOrbitPoint; related #303, #316, PR #507. A Three.js forum thread names the same pairing (https://discourse.threejs.org/t/camera-zoom-in-and-out/57323/12). I found no issue titled "stop() causes jump" (search was shallow; UNVERIFIED absence).
- Recommended way to pick a new orbit point mid-gesture: none documented. Safe pattern by the source: call setOrbitPoint only when the controls are at rest (listen to 'rest'/'sleep' events, README), or avoid focalOffset entirely: compute the new target yourself and call setTarget(x,y,z,false) + setPosition to keep the camera pose (or use setLookAt with enableTransition false). Not verified in code; test.
- update(delta) + frameloop="demand": README example renders when update() returns true. R3F docs (https://r3f.docs.pmnd.rs/advanced/scaling-performance): invalidate() "will not render immediately, it merely requests a new frame", multiple calls do not cause multiple renders; camera controls mutate the camera, so call invalidate on the controls' change event; drei does this automatically. Nothing documented about stutter from per-event invalidate. Risk (analysis, not a source): if the loop ticks update(delta) only when something invalidates, the delta passed spans idle gaps (a long first delta after a pause makes SmoothDamp take one big step) and the spring tail needs invalidate to keep running until 'rest'/'sleep'. Make sure update() is called every rAF while update() returned true last time, with delta clamped (e.g. <= 1/30).
  - Could make motion not smooth: first frame of every gesture after an idle gap gets a huge or zero delta -> a hitch exactly at gesture start.

## 2. Sketchfab
- Controls (help.sketchfab.com/en/articles/16152696): orbit with left drag, pan right-drag or Shift+left, zoom wheel/pinch/Ctrl+drag; double-click on model sets pivot to that point; double-click background re-centres on bounding box.
- No official or reverse-engineered numbers for inertia, damping or zoom easing were found (searched once; Sketchfab Viewer API docs not fetched). Owed: measure by recording a Sketchfab model with rAF/Performance (e.g. release a flick drag and time the decay; scroll one notch and sample camera position per frame).
  - Could make motion not smooth: our "Navigate" is modelled on Sketchfab, which (from experience, UNVERIFIED) glides after release and eases wheel zoom; ours has no inertia at draggingSmoothTime 0 and no zoom easing, so it feels stepped by comparison.

## 4. three.js OrbitControls and others
- three.js OrbitControls (dev branch source, fetched): enableDamping false by default; dampingFactor 0.05; zoomSpeed 1.0; per-frame update: theta += delta.theta * dampingFactor, then delta *= (1 - dampingFactor) (l.715-720), i.e. a frame-rate-dependent exponential decay (half-life ~13.5 frames = 225 ms at 60 fps). Wheel scale = 0.95^(zoomSpeed * |deltaY*0.01|) (l.946-949): 100 px -> 0.95^1 = 5 % per notch (vs 15.7 % in camera-controls). Damping applies during drag and after release (inertia); requires controls.update() every frame.
  - Could make motion not smooth: our wheel notch is ~3x three.js's step, undamped.
- Babylon ArcRotateCamera: wheelPrecision default 3.0 (arcRotateCameraMouseWheelInput.js, via unpkg search result); zoom shares the camera `inertia` (default 0.9 from memory, UNVERIFIED), https://forum.babylonjs.com/t/arcrotatecamera-and-zoom-sensitivity/33046. Forum comparison: https://forum.babylonjs.com/t/camera-control-similar-to-blender-or-sketchfab/8516 (anecdotal, three.js felt "snappy and proportional").
- Spline, Polycam, three.js Editor: no source fetched. Owed.
- Guidance (engineering reading): damping both during drag and after release is the norm in the viewers above; draggingSmoothTime 0 means "no filtering of input noise", which exposes mouse-rate and frame-timing irregularities.

## 5. Browser input
- Chrome 60 "aligned input" (https://developer.chrome.com/blog/aligning-input-events): wheel, touchmove, pointermove, mousemove are delayed and dispatched "right before the requestAnimationFrame callback"; discrete events (mousedown, keyup) are not. Mice "typically deliver at 100 Hz, but can reach 2000 Hz"; monitors typically 60 Hz. Hence at most one wheel/pointermove event per frame is dispatched (coalesced); getCoalescedEvents() (MDN https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents) returns the merged intermediate events.
  - Could make motion not smooth: with a 1000 Hz mouse, one drag event per frame carries a summed delta (fine), but events then arrive exactly one per frame so any frame that misses its rAF alignment (60 vs 144 Hz mismatch, long task) produces 0 or 2 events in a frame: visible judder with no smoothing to hide it.
  - Applying deltas per event vs per frame: when event dispatch is rAF-aligned the two are equivalent; if the app calls render outside rAF (invalidate from the event handler, R3F then renders in its own rAF) the delta can land one frame late.
- MDN deltaMode: 0 pixel, 1 line, 2 page; "do not assume pixels". Chromium Linux wheel: kernel gives REL_WHEEL_HI_RES units of 120 per detent (Documentation/input/event-codes.rst); Chromium Linux default 100 px/notch with "smooth scrolling" flag changing scroll animation but wheel event deltas stay per-notch, UNVERIFIED. High-res wheels (Logitech etc.) may emit fractional notches, e.g. deltaY 4-20 many times per burst: then steps are smooth by themselves. MEASURE deltaY/deltaMode/event interval on his mouse.
- pointerrawupdate: not examined; unnecessary unless input latency is the issue.

## 6. Frame pacing on Linux Chromium (NVIDIA, KWin X11)
- Sources found are old (2018): Chromium issue https://issues.chromium.org/40954503 (tearing only when KDE suspends compositing); NVIDIA forum https://forums.developer.nvidia.com/t/chromium-video-stutter-in-390-25-in-addition-to-previously-mentioned-performance-issues/57929 (driver 390.25 gave 60.00 vs 59.95 Hz timing mismatch -> stutter); blog https://blog.psy-q.ch/blog/2018/01/24/yet-another-way-to-get-a-tear-free-stutter-free-desktop-with-plasma-kde-and-nvidia/ (__GL_YIELD=usleep, KWIN_TRIPLE_BUFFER=1, ForceCompositionPipeline can itself stutter). Nothing current for 2026; treat as hypotheses, not facts.
- Measured "60 fps steady" is an average. It does not show frame-time variance, dropped/duplicated frames at the compositor, or a monitor at 144 Hz showing 60 fps content (uneven cadence if the display is not 60 Hz or if rAF runs at 144 but the app invalidates at event rate).
- How to measure: chrome://gpu (GL renderer, "Vulkan", compositing), Performance panel frame timeline (frame durations, "Dropped"), rAF timestamps logged during a gesture (look at the standard deviation and any interval > 1.5x refresh), DevTools Rendering > "Frame Rendering Stats", about:tracing / chrome://tracing with "input,gpu,viz,benchmark" categories (Viz "DisplayScheduler", "BeginFrame" missed). `--disable-frame-rate-limit` is a diagnostic only (uncaps rAF; it hides, not fixes, pacing).
  - Could make motion not smooth: uneven rAF cadence (e.g. 16.7/33/16.7 ms) under KWin + NVIDIA reads as stutter even at an "average" 60 fps.

## Ranked likely causes for OUR setup, with cheap tests

1. Wheel zoom is unsmoothed because the wheel handler sets `_isUserControllingDolly`, which selects draggingSmoothTime 0 (source l.850, l.2104), with 15.7 % radius per 100 px notch. Test: log `cc.distance` per rAF during 3 notches; staircase (each notch changes value in 1 frame, then flat) = confirmed. Change: set draggingSmoothTime ~0.05-0.1 temporarily, or reset `_isUserControllingDolly` after wheel; re-log: a curve over ~150-250 ms = fixed. Also cut dollySpeed so a notch is ~5-8 %.
2. stop() snaps current state to end state at each gesture/burst start. Test: before cc.stop() record camera.position; after record again; the difference (in px at the screen) at bursts that begin within ~300 ms of a prior motion; non-zero = pop. Replace by setting end=current (no jump), e.g. via a `setLookAt(...current..., false)`/own helper that copies current into end.
3. setOrbitPoint at gesture start mid-transition (and inside the same frame as stop()): library says "SHOULD NOT RUN DURING ANIMATIONS"; issue #424. Test: compare camera world position and view matrix before/after the setOrbitPoint call (should be identical to 1e-6); then count `rest` events (call only when rested) and see if the pop remains. If pose changes, it is a defect.
4. Forced layout per wheel event (inverted timestamp condition, l.812-820). Test: Performance recording during a wheel burst; look for "Recalculate style / Layout" inside wheel handlers, or monkey-patch getBoundingClientRect counter: expect count == wheel events instead of 1 per scroll start. Fix: patch/override via `_getClientRect` or set dollyToCursor handling ourselves.
5. update(delta)/invalidate cadence under frameloop="demand": a large or zero delta on the first frame after idle, spring tail stopping early. Test: log delta passed to update() per frame over a gesture; any first delta > 50 ms, or a gap in rAF while update() returned true = confirmed. Fix: invalidate each frame while update() returns true, clamp delta.
6. Frame pacing / display: uneven rAF cadence on KWin X11 + NVIDIA, 60 vs 144 Hz mismatch, or wheel deltaY pattern of the mouse. Test: log rAF intervals and event timestamps during a 5 s drag; compute stddev and count of intervals > 20 ms (60 Hz) or > 9 ms (144 Hz); check `xrandr` refresh rate and chrome://gpu. If stddev < 1 ms and no long frames, cause 6 is ruled out. Also log wheel deltaY/deltaMode: values ≠ ±100 or fractional change cause 1's step size.

Open / unverified: Sketchfab numbers, Blender Drag Immediately/0.4 deg text and wheel-smoothing, Spline/Polycam, Chromium Linux wheel-delta and smooth-scrolling-flag behaviour, current KWin/NVIDIA guidance.
