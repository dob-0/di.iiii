## 2026-10-21 — `di update` names itself to the hub, waits out a 429, and says who answered when it gives up

- Cause (code reading + a test-copy measurement by the launching session; live proof still owed): serverXR's visitor bouncer (`serverXR/src/appVisitors.js`) counts a program without a contact in its User-Agent (Node's default `node`) as anonymous: 30 API reads a minute per address against 300 for an identified app, shared with every other unnamed program from that address. The update check's health read was anonymous.
- `scripts/di/channels.mjs`: the health read sends `User-Agent: di/<installed version> (+https://diiii.xyz/for-apps)` (new `userAgent()`), which `classifyUserAgent` classifies as an app.
- `hubCommit` retries on 429 and 503 only — Retry-After (seconds or HTTP date) else 2 s, 4 s, 8 s; ≤ 3 retries; ≤ 30 s total wait; per-request timeout unchanged. The failure line carries status, `server`, `cf-ray`, `retry-after`, retry count and the first 120 body characters.
- Tests: `scripts/di/channels.test.js` 18/18 pass; the 8 new cases fail on the old code (shown: 6 retry/line cases, then 2 User-Agent cases). `scripts/di` as a whole: 4 failures in `openFile.test.js` / `oneAddressPrinted.test.js`, identical with and without the change (missing `dotenv` in serverXR, `diiii.localhost` not resolving in the cloud container).
- Not done: scripts/di has no shared request helper, so the other hub requests (`login`, `sync`, `share`, …) still send Node's default User-Agent. Not tested: a real 429 on an install; the next failure line on the install is the live proof.
