## 2026-11-20 — `di monitor feed`: a machine's chats feed set by a command

- Why: a machine shows its chats in the Monitor only when `~/.di/monitor.json` holds a feed with panel `chats` and a command. Today that is a hand edit of JSON, so most machines never report their chats; the owner wants every session of every device in one Monitor.
- What: `di monitor feed add|remove|list` in `scripts/di/monitorFeed.mjs` (all the logic). `monitorReport.mjs` only gets the import, two usage lines, `feed` in `parseMonitorArgs` and one dispatch line; `args.mjs` learns `--command`, `--id`, `--title` as value flags (the shared parser makes every other flag a boolean); `ui.mjs` gets one help line. In all the PR changes 8 files (`git diff --stat origin/dev...HEAD`): those four code files, the test `monitorFeed.test.js`, `docs/START-HERE.md`, the Wiki entry (`src/wiki/wikiContent.js`) and this note.
- Rules it keeps: panels `chats` and `credits` only (anything else is a usage error, exit 2). `add` replaces the feed with the same panel and id or appends it, keeps every other key and feed, writes through `atomicWrite.mjs` (temp file in the same folder, rename), mode 0600, keeps the old bytes once as `monitor.json.bak-<YYYYMMDD-HHMMSS>` before a changing write, and writes nothing when the feed is already set. A file that is not a JSON object is refused with its line and column and stays byte for byte. Every changing action ends with `undo:` and the backup path.
- `--check`: runs the command once under the Monitor's own limits and reads the output with the Monitor's own readers (`serverXR/src/monitorChats.js`, `monitorCredits.js`), so a command that passes is one the Monitor accepts. A chat list must carry `generatedAt`, the time it was made as a number of seconds since 1970: the reader keeps it only as a number above 0, and a list without it is shown as stale, so `--check` refuses it. The limits in `CHECK_LIMIT_MS` (4 s for chats, 8 s for credits) copy what `serverXR/src/monitorStore.js` runs; the server waits 6 s around the chats command but stops the command itself at 4 s. `limitFor()` takes the credits limit from the store when it exports `CREDITS_COMMAND_MS` (the credits-slow-probe fix raises it to 30 s because a cold probe takes 12 s), so `--check` follows that change by itself; a test reads the store's source and fails when a limit stands there that `--check` does not know.
- A file that changes while `--check` runs: the check takes up to 4 s (8 s for credits, 30 s in a tree with the credits-slow-probe fix), and the first read of `monitor.json` is that old when the write comes. So the file is read again right before a changing write. Other bytes than the first read saw, a file that appeared, or one that vanished, refuse the write: nothing is made, no backup, the other edit is kept, exit 1, and the message is "<file> changed while this command ran, so nothing was written. Run the command again." The same bytes written again (an editor saving without a change) do not stop it.
- Tested: `scripts/di/monitorFeed.test.js` (a temp folder per test, HOME and `DI_MONITOR_CONFIG` pointed at it), plus the CLI run as a process. Five conditions were flipped one at a time (idempotent check, backup once, refuse invalid JSON, mode, atomic rename) and each turned the test red; after the review three more were flipped (the read before the write, the `generatedAt` refusal, the shapes in the usage text) and each turned its tests red too.
- Not done: running it on a second machine (the lead's rollout); `scripts/monitor-join.sh --chats-command`, which the brief marked optional.
- Undo: revert the commit. On a machine, `di monitor feed remove chats`, or copy the printed backup back.
