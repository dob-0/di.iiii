### A1 — Truss clamps, washLevelOf, the versions cap, the strobe cap (ref preview/rigbuilder-13)

**Findings**

1. **HIGH — the desk's own `strobe` effect flashes the dimmer 20 times a second, and the room draws a dimmer flash with no cap.** `serverXR/src/lighting/fx.js:189-194`:
   `const slice = Math.max(FRAME_MS * 2, Math.floor(beatMs / 8 / FRAME_MS) * FRAME_MS);` with `FRAME_MS = 25`, `bpm` clamped to 20..300, default 120.
   Scenario: at the default 120 bpm, beatMs = 500 and slice = max(50, floor(62.5/25)*25 = 50) = 50 ms, so the effect runs at **20 flashes/s**. Every bpm ≥ 60 gives 20 Hz, and 20 bpm gives about 5.3 Hz. So any fixture running the desk's strobe effect breaks the 3-per-second rule on the Art-Net output itself. `serverXR/src` has no reference to `strobeCap`/`MAX_STROBE_HZ` at all. The same bypass shows in the visualiser: `dmxDecode.decodeDmx` turns the dimmer byte into `level` straight away, and `capStrobeHz` only ever sees the shutter or rate channel. A console that chases the dimmer (or this effect) therefore draws a flicker at the DMX frame rate through `rigFlash` `steady`/`level` (`dmxPose.js:111`) and the spot intensity, and no cap applies. The cap covers "strobe" as a shutter mode, not flashing as such.
   Smallest fix: in fx.js, floor the strobe slice at `1000 / MAX_STROBE_HZ` ms (whole frames, ≥ 14 × 25 ms), using a server-side copy of the constant. For the visualiser, add a limiter on level rises (at most 3 rises from ≤ 0.5 to > 0.5 per second, per lamp and for the room) where dmxPose applies `level`. fx.js dates from 2026-09-03, not today, but it is a live path the scope asks about ("the desk's own strobe").

2. **MEDIUM — the DMX encoding rounds the capped rate UP, so the value written plays faster than 3 Hz by the fixture's own table.** `src/rigbuild/dmxDecode.js:203-206` (`strobeValue`) and `:198-201` (`rateValue`) use `Math.round(r.from + frac * (r.to - r.from))`. The comment at `:255-257` says "the resulting rate is <= MAX_STROBE_HZ", and it is not. Proven with `encodeDmx` → `decodeDmx` on the shutter tables in `assumedProfiles.js`, asking for 3 Hz, which is the default for every look with no `strobeHz` (`lookStrobeHz`): table `{51..240: [1,25]}` → value 67 → **3.03 Hz**; `{4..203: [1,20]}` → 25 → 3.01 Hz; `{1..255: [1,20]}` → 28 → 3.02 Hz; `{5..255: [1,25]}` → 26 → 3.02 Hz; `{11..132: [1,20]}` → 24 → **3.04 Hz**. Asking for 2.99 Hz gives the same values. The dedicated rate channel `[0.5,25]` happened to round down (2.96 Hz).
   Smallest fix: take the largest DMX value whose decoded rate is ≤ the capped Hz, i.e. `Math.floor` for an ascending range, and add a round-trip test `decodeDmx(encodeDmx(3)).strobeHz <= 3` over every table in assumedProfiles.

3. **MEDIUM — the cap is per lamp, but the rule is about flashes a person sees.** Lamps at different capped rates add up. `RigFlashes.jsx:58` flashes each desk-driven face at its own `lamp.hz`, faces not driven by a desk use the shared 3 Hz `strobeEnv`, and `SpotLightObject` beams strobe at their own `beam.strobeHz`. All are phase-locked to `Date.now()`, but only lamps at the *same* rate coincide. Scenario: a console drives two strobe profiles at "3 Hz". By finding 2 they decode to 3.03 (capped to 3.00) and 2.92 (the `{4..103:[1,20]}` table gives value 14 → 2.92 Hz). The two trains of 22 ms pulses drift against each other and give about 5.9 separate flashes a second in one view, while every lamp individually passes `capStrobeHz`. The same happens with a look's own strobes at 3 Hz against a desk-driven lamp at 2.5 Hz. Smallest fix: draw every strobe at one room-wide rate (the fastest lit one, capped) on one phase train, or quantise to divisors of 3 Hz (3, 1.5, 1), so the union can never exceed 3 per second, and test it by counting the union of the pulse trains.

4. **LOW — the matte-steel fix covers only the sloped crane line. The other hangs keep the metal that "renders almost black".** The reason is in `scripts/place/rig-lib.mjs:805-809` itself: metalness 0.8–0.9 with no environment map vanishes in a dark hall. Still at high metalness on the same ref: the straight-header safety steel `:1103` (`metalness: 0.9`, 12 mm wide), the spreader `:1099` (0.7), the xflat junction `:1376` (0.8) and the xflat beam clamps `:1390` (0.7). The versions that use the straight header or the xflat hang can still read as floating, the complaint the new clamps answered for the crane line. Fix: use `STEEL_METALNESS`/`STEEL_ROUGHNESS` (and `RIGGING_EMISSIVE` on the thin parts) there as well. A smaller label defect in the same function: the safety-steel clamp (`:990-996`) is named "on the back girder" but sits at `crane.z_m - leg_spread_m/2`, the side bridle leg `a` (k=0) calls "audience-side" (`:976`, `:983`). Either the geometry or the label is wrong.

**Refuted**
- ESM/CJS mirror drift: `RIG_VERSIONS_CAP`, `variantId` and `normalizeRigVariant` (with `copyOf`) are textually identical apart from `export` (diffed ESM 840-876 against CJS 743-779), and so is `planText`.
- Duplicate entity ids across the 3 picks: every clamp, steel and hoist id carries `p.i + 1`, and the straight-header branch (`hoist-N-spreader`) runs only when `picks_u_m` is absent (`:1089-1095`).
- The clamp boxes floating or overlapping: `box` is base-anchored (`:820`), so a clamp spans legTopY → legTopY + clamp_drop = girder_bottom. The steel clamp at x+0.12 ±0.04 does not overlap clamp `a` at x ±0.06.
- A stored `beam.strobeHz` or `rigFlash.hz` above 3 drawn raw: both go through `strobeEnvelope`, which calls `capStrobeHz` (`rigFlash.js:29`).
- `washLevelOf` on old projects: an untyped key (`column-faces`) still counts (`type === undefined`), and this is tested in `rigFlash.test.jsx:135-142`.
- The versions cap as a safety defect. A related edge, noted here and not counted: `.slice(0, 32)` runs *before* invalid entries are filtered out, so 30 invalid entries ahead of 6 valid ones make `normalizeRigVariant` return `null` (proven with node), and duplicate sibling ids are kept. copy-version already warns about a self entry past the cap (B2's area).

**Not read**: `scripts/rigbuild/truss-hang.test.js` in full (it exists on the ref); no vitest file was run in A1; `show-loop.mjs` beyond its strobe lines; the fixture library beyond its two `par` entries (up-pl5403, up-cob200). Whether any rig hangs up-cob200 at a wash position, where the hard-coded `WASH_TYPES = {'up-pl5403'}` would ignore it, was not settled.

### A2 — Ground-mover policy guard and the ground scenes' safety rules (ref feat/moxir-ground-scenes)

**Findings**

1. **HIGH — `requiresLaserSignOff` is a word in a prose string, not a gate. The committed look `gs-laser-roof` drives the Class 4 laser at 60 %.** `scripts/rigbuild/ground-scenes.mjs:117-122` sets `[LASER_GROUP]: on(0.6, RED, { rule: 'laser-into-roof', a: 18 })`, and `:172` only appends the text "requiresLaserSignOff" to `intent`, which is truncated with `.slice(0, 480)`. `withScenes` (`:199-208`) forces the laser to 0 in the *existing* looks and then adds `gs-laser-roof` with 0.6 to both versions' `looks` (committed in `moxir-2026-10-17-minimal-ground.json:1497` and `-full-ground.json:1655`). The only thing that keeps it dark is that the look is not a cue in the loop, and that is checked by a test (`ground-scenes.test.js:73-84`), not by the runtime. A grep of `src/rigbuild`, `src/rigMirror` and `serverXR/src/lighting` finds no code that reads a laser flag, so selecting that look in the room, in the desk's look playback or in a future scene deck sends the level out like any other group. Scenario: an operator picks "Laser into the roof" from the look list on the desk-driven room → DMX for the laser group at 0.6, with no sign-off recorded anywhere. Smallest fix: store the look with the laser at 0 plus a real field (e.g. `requiresLaserSignOff: true`, or a `laserArmed` level kept apart from `levels`). Make the level path (deskLookValues/useRigLook/scene deck) zero any laser-class group unless a stored, named sign-off exists, and test that path, not the rig file.

2. **MEDIUM — the guard measures only the dance-zone box. A loop look rakes the aisle, where the analysis itself says people stand and sit, at 1.9 m.** `ground-movers.mjs:135` checks movers against `zoneBox(hall, 'dance', [0, eye])` only (x ±5.35, z 7.5..48). The aisle between that box and the column faces (x 5.35..11.6) is in `PLACES` as "crowd overflow, people stand and sit here" (`:180`), and the ground movers stand in it. Measured with the module's own `coneRays`, using the aisle box and ignoring the first 1.5 m from each lens: in `gs-cross-beams`, which is a cue in **both** loops, `rig-beam380-columns-6-01` (lens [-10.66, 0.59, 12]) has its lower cone edge at **1.90 m** at [-9.1, 1.9, 12], under the 2.5 m eye height. The other 16 poses (rest aims and every other look) are clear. Smallest fix: test movers against every floor a person can stand on (dance zone + aisles + pit, i.e. the same wide box the laser rule already uses), excluding a stated radius around the lens, and lower `in_deg` in cross-beams (48° for beam380) until it passes.

3. **LOW — the effects in the pit have no distance rule. The CO2 jets stand 0.4 m from the crowd rail.** In `moxir-2026-10-17-full-ground.json` the CO2 is at `pit_m: 0.9` and the sparks at `pit_m: 0.4`, with the barrier at `pit_m: 1.3` and `h_m: 1.1`. That puts 6 CO2 jets 0.4 m and 4 spark machines 0.9 m behind a rail the crowd leans over. The test (`ground-movers.test.js`, "never hang an effect") only asserts `0.3 <= pit_m < 1.3`. The notes say "UNVALIDATED" honestly, and the loop's "Spark hit" cue fires nothing (effects are not simulated or driven), so this is a missing rule, not a false claim. Fix: a `min_clear_to_crowd_m` per effect class in the policy, checked like the mover rule, left as "owed" until the maker's figure is read.

4. **LOW — the guard's own reach has latent holes (none fire on today's rigs).** (a) A laser is recognised only by `code === 'UP-LA40WF'` (`:47`). A second laser model is neither a mover nor a laser, so it gets no check at all. Use the library `category === 'laser'`. (b) The laser rule measures 3 m from y = 0 over `z [stage.front, door]` (`:136`). It leaves out the DJ riser deck (1.2 m, so the rule there is 4.2 m absolute) and the crew floor behind it. (c) "Cannot be dodged by name" (`ground-movers.test.js`) only lists files matching `^moxir-2026-10-17-`, so a ground version of another show date escapes both tests. (d) `groupOf` matches entity ids by prefix (`rig-${g.id}-`), so a group `beam380` listed before `beam380-columns` would claim the latter's lamps and could class them as non-movers. No such pair exists today (checked: no id is a `-`-prefix of another in either version).

**Refuted**
- A beam that clears 2.5 m at rest but dips into the dance zone during a fade: measured, not reasoned. With the room's own `blendEntities` between every consecutive pair of loop cues, wrap included, at t = 0.05..0.95 in steps of 0.05 (152 poses minimal-ground, 190 full-ground), `lowestInZone` against the dance zone found **0** violations. The desk's own pan/tilt interpolation was not modelled.
- mountHeight on the wrong face: every floor mount in rig-lib places the base at y = 0 (`column-bases`, `backdrop-floor`, `booth-pit`), and no group field lifts it (grep for plinth, lift, y offsets finds nothing).
- Loop length arithmetic: holds sum to 79 s (minimal-ground) and 81 s (full-ground), every fade ≤ its hold, inside 60–90 s.
- Strobe events per second in the cue lists: the only strobe-capable group (COB200) is lit only by `gs-blinder-hit`, cut in and cut out at fade 0 over a 3 s hold, i.e. 2 transitions in 3 s. No group in either version is a strobe-category fixture (tested).
- Bypassing the guard with a mover type outside the list: `isMover` is "has `pan_tilt_deg`", and every mover in both versions (B380F, 250BSW, HK1915) is recognised.
