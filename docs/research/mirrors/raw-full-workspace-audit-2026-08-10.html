Raw is a description, not a runtime

The pieces of a combined multimedia workspace — code authoring, page publishing, asset storage, sandboxed execution, deferred jobs — are all already built in di.iiii. None of them are reachable from a node. And the thing that would make them reachable, an evaluator that actually runs, was never built.

What follows is a code-level audit of the Raw lane and its surroundings, plus a survey of how eleven shipped node-based environments solve the same problem. Every claim about di.iiii carries a file and line. Every claim about the field carries a source. The recommendation at the end is one path, ordered, with an explicit list of what not to build.

Part one

The workspace already exists. It is just not in the graph.

The complaint was that there is no easy way to manage code and pages in Raw. That is true, and the reason is more interesting than "it wasn't built yet." Almost all of it was built — in Studio, in serverXR, and in the publish path.

presentationState.codeFiles[]Studio only

A real multi-file HTML/CSS/JS editor: file tabs, add/rename/delete with automatic href/src rewriting, zip and folder import, zip export, starter templates, asset-URL insertion at the cursor. StudioShellPanels.jsx:1212–1470. The editing surface itself is a plain MUI textarea — no highlighting, no diagnostics.

grep codeFiles src/raw returns zero hits. No node type reads it; Raw imports nothing from codeFilesBundle.js.

Sandboxed page executionpublish path

Published pages run user HTML/JS in a srcdoc iframe with allow-scripts allow-forms … and — deliberately — without allow-same-origin unless the owner opts into deviceAccess. PublicProjectViewer.jsx:36, 239, 252. A live document read over SSE, not a static export.

The security primitive for running untrusted code in a page is therefore already in the product, already reviewed, already shipping to every visitor of every published space.

git push → live pageserverXR

POST /api/github/webhook (serverXR/src/index.js:1197), HMAC-verified, mounted pre-auth-gate. On push it pulls the repo with an installation token, reads a di-space.json manifest, uploads referenced binaries, rewrites their URLs, and PUTs the result as the space's codeFiles, then points publishedProjectId at it.

Deferred, approved, re-authorized actionsserverXR

The approval gate is a working durable-action system: gateOrApply writes a pending_actions row and returns 202; nothing runs until a signed decision arrives from di-bo over POST /api/approvals/decision. Authorization is re-derived at execution time, never restored from a snapshot (approvalGate.js:20-23); intent_hash binds the decision to exact arguments; it fails closed on TTL.

That is most of what a "work automation" node would need on the server side, and it already exists. What it does not have is a user-registrable executor — the six kinds are fixed (approvalGate.js:245-257).

The single most actionable line in the whole audit

setPresentationState, setPublishState, upsertAsset, deleteAsset and setProjectMeta are all real ops with real inverses in src/shared/projectSchema.js:905-948. Undo works. Sync works. Collaboration works.

No Raw component emits any of them. The gap between "Raw cannot manage pages" and "Raw can manage pages" is UI, not architecture.

Part two

Three absences, and only one of them is on the critical path.

There is an evaluator, but no scheduler

nodeGraphRuntime.js is a pull-based, memoised-per-pass recursive evaluator with one switch (node.typeId) carrying twenty cases. Nothing pushes. There is no frame loop — except a conditional requestAnimationFrame that exists only to advance a clock value, and only if a time node happens to exist anywhere in the document (useGraphClock.js:3). Evaluation is triggered by React re-render.

Everything else in this section follows from that one fact.

A node type cannot define its own behaviour

A registry entry is pure data. There is no evaluate, compute, update, or component field anywhere. All behaviour is hardcoded by typeId in consumer modules: 49 branch sites across 8 files, plus type-id-keyed tables (one of which, WINDOW_DEFAULT_POSITIONS, names six node types that do not exist).

Adding one working node type touches up to five files. Stopping after the registry entry fails silently: computeNodeOutput falls through to return node.values[portId], and an unhandled panel type renders as a generic text panel.

The one fact that makes all of this cheap

The schema layer never imports the registry. typeId is a free string and values is unvalidated, so adding a node type costs zero migration. Old documents are untouched; unknown types persist silently. Whatever is built here does not need a schema version bump.

The reverse is the hazard: renaming a port silently orphans every stored edge and every values key, and nothing detects it.

Part three

What eleven shipped environments agree on.

TouchDesigner, Max/MSP, Pure Data, Unreal Blueprints, Notch, Resolume Wire + ISF, Isadora, Vizzie, cables.gl, vvvv gamma and Nodes.io. Different decades, different industries, no shared lineage. They converge on four things.

Code declares its own ports

Every system that successfully put text code inside a node graph derives the node's interface from the source text, rather than making the author declare it twice.

Two refinements are worth taking whole. Isadora gives each parameter a stable 1–4 character id distinct from its display name, so renaming a parameter does not break saved patches — the thing Max's XML shader binding lacks. And ISF separates LABEL from NAME so the identifier stays a legal one, and carries an IDENTITY key: the value at which the parameter is a no-op, which lets a host bypass the node entirely.

Editing ISF loses parameters.

Open complaint on the Resolume Wire forum. Editing a code node's source changes its declared interface, and the graph loses already-wired connections and values.

That is the failure to design against before building the feature: match by name, preserve connections and values across recompile, mark removed inputs as orphaned rather than dropping wires silently, surface added inputs. cables.gl solves the same problem by rebuilding every instance and re-linking by port name, logging could not set port X, probably renamed port ? when a name moved.

The node is an interface; graph and code are both implementations

MaterialX — the industry standard, and the cleanest resolution of "is code a node or a node's body" anywhere in the survey — splits a node into three layers. A nodedef is the declared interface: typed inputs with defaults, typed outputs, and it is versioned. A nodegraph is a subgraph acting as an implementation of that nodedef. An implementation is source code for a particular target — OSL, GLSL, MDL.

One node type, N implementations, one of which may be a subgraph and others of which are text per backend. That collapses port promotion and the code node into a single mechanism rather than two features that have to agree with each other.

Shaders are not a system to build here — they are a view onto an IR already in the stack

three.js materials already are a node graph. TSL is its text form; it compiles to both GLSL and WGSL through NodeBuilder, the standard node materials are built on it, and it interoperates with MaterialX. The three.js wiki says so directly: "modern 3D authoring software uses Shader-Graph based material composition."

So the missing material node category is not a new subsystem. It is a surface over an existing node IR, and it comes with the WebGL/WebGPU split already solved.

Two kinds of subgraph, not one

Unreal ships both, and the difference is load-bearing. A Function is a real call with a declared signature, overridable, single exec exit. A Macro is copy-pasted into the caller at compile time, and can therefore have multiple execution outputs and contain latent (suspending) nodes. ForEachLoop, DoOnce, Gate and FlipFlop are all macros for exactly that reason.

If the only subgraph abstraction is "a function", a user can never author a loop-with-body node. Resolume Wire is the live proof of the alternative: it has hundreds of node types and no subpatches at all — and consequently a minimap, a node search, an auto-layout, a comment-as-frame convention, an unused-node cleaner and a marketplace, every one of them compensation for the missing feature.

Ports carry two orthogonal properties, not one

Isadora encodes both in geometry: shape is scaling state (circle / square / triangle), fill is type mutability (solid / hollow). Resolume Wire encodes a different pair: colour is the data type, shape is the update discipline — circle for signal (frame rate), rectangle for event (discrete, several per frame), diamond for attribute (compile-time only; changing it recompiles the patch).

Wire's three flow types map onto di.iiii almost exactly: the render tick, user and network events, and scene-build constants. With one warning attached. Attribute-flow parameters were un-automatable for six years — Wire 7.27.1, July 2026, is the release that finally notes "they cause the whole patch to recompile. We have made this a lot more efficient, so now this limitation is no longer there." Make recompile cheap on day one or ship the same hole.

The CPU/GPU boundary must be visible in the graph

Vizzie 2 made its modules accept both CPU matrices and GPU textures transparently. The result, from Cycling '74's own forum: users reported bad performance, and the cause was that one upstream node they could not see was emitting matrices, so an entire GPU-capable chain silently ran on the CPU. The only escapes offered were pinning the old module version or embedding it in the parent patch.

Isadora made the opposite call — Video CPU and Video GPU are two types, and you convert a chain actor by actor. Tedious and honest. Jitter's rule, stated by Cycling '74: "once your data is on the GPU it should stay there." Sending a texture straight to a preview window silently triggers a readback.

Part four

The sandbox question is settled, and it was measured here.

Running user-authored code at frame rate in a browser tab was the open feasibility question. It is answered. The numbers below were benchmarked on this machine against quickjs-emscripten@0.32.0, not quoted from documentation — no published benchmark of this library's call throughput exists.

That last row is the one that decides the architecture. SES and iframes cannot interrupt. One while(true) in a hardened-JavaScript compartment freezes the page permanently; a catastrophic regex does the same. QuickJS stops both, and returns a clean JS error rather than a crash — as do its memory and stack limits.

Figma is the precedent and the reason to trust the shape. They shipped a Realms-based plugin sandbox, had escapes privately disclosed, and replaced the whole thing with QuickJS-in-WASM in nine days. Their stated reason is structural rather than defensive: because a sandbox value is an opaque pointer into linear memory, "it's not possible to confuse objects from outside with objects from inside because the object representations are too different." The bug class is not patched, it is unrepresentable. Their bridge is a membrane of roughly 500 lines, and plugin code never holds a direct reference to a Figma object.

The hazard nobody documents

A single leaked handle aborts the entire WASM module — Assertion failed: list_empty(&rt->gc_obj_list) — taking every co-hosted context with it. In a page running twenty code nodes in one module, one leak kills all twenty. The agent hit this twice by accident inside a 200-line benchmark. Disposal discipline has to be written into the API, not into reviewers' heads.

The strongest counter-evidence is Val Town, who evaluated exactly this and rejected it: "we'd be miles away from NPM or Node compatibility." That objection does not apply here. di.iiii's node API is small and its own. QuickJS loses when users expect npm; it wins when the surface is a curated set of ports.

Part five

Four expensive lessons, paid for by other people.

Do not build a bespoke code editor

Darklang's entire premise was a structured editor with no parser — "to never ever have a syntax error again" — with git and grep named explicitly as the disease. The retrospective, in their own words: the editor was ~50% of the codebase, 200 ReScript files and 50k lines, in a language that could never be ported to Darklang itself. Users rated it "somewhere between 'Ok I guess' and 'probably the worst part of Darklang'."

By removing the editor, and the backward-compatibility requirements, we've unlocked incredible progress… Overall, we accomplished more in February and March than in the past two years combined.

Paul Biggar, Darklang blog, March 2023. They deleted the whole thing and replaced it with tree-sitter, an LSP and a VS Code extension.

di.iiii has zero editor libraries installed — no CodeMirror, Monaco, Ace, Prism or Shiki. That is currently an absence; it should become a decision.

Monaco is disqualified, and not on size. Its own FAQ, still the live text on main: "Is the editor supported in mobile browsers or mobile web app frameworks? No." The request has been open ten years with 211 reactions; the keyboard does not open on Android and there are no touch selection handles. Size is the second reason — a realistic JS/TS Monaco is 1117 KB gzip plus a 92 KB editor worker plus a 1512 KB TypeScript worker, and thirty instances cost 23 MB of heap.

Three tiers, not one editor, all figures measured here:

Thirty CM6 instances is 103 ms and 4 MB — survivable but unnecessary. Promote on focus, demote on blur. Two rules follow from the measurements: use transform: scale() and never CSS zoom (there is an open CM6 bug filed on exactly that, by someone building a pinch-zoomable mobile code editor), and set editor CSS to ≥16px or iOS auto-zooms on focus and fights the canvas camera.

The caveat that matters: those numbers come from Chromium touch emulation, which cannot reproduce iOS selection handles, the magnifier, or Gboard composition. CM6 has an open iOS bug where drawSelection() renders the native handles invisible. Which makes the plan file's open question #4 — "Does this workspace need to work on a phone?" — the thing that decides the tier, not an aside.

Do not plan on compiling the graph to code

Epic built Blueprint Nativization, shipped it across five engine versions, and deleted it: "Blueprint Nativization will not exist in UE5." What replaced it is nothing automatic — a C++ base class with a Blueprint subclass, and a Header View that emits declarations only, as a scaffold for hand-porting. Enso, whose whole premise is bidirectional graph↔code, had to constrain the language to make it work.

Cache pure evaluation, per tick

Unreal's pure nodes are pull-evaluated and not memoised, so they run once per consuming connection. Documented real cases: a pure array getter feeding a six-element loop runs 13 times; a filter inside nested loops runs 35,301 times to produce ten print statements. There is a correctness dimension too — a pure random node hands a different value to each consumer of the same wire.

Raw already memoises per pass, which is right. The thing to preserve when a real scheduler lands is that a volatile node (time, random) is a declared opt-out, not an accident.

A node graph has to be the natural notation for its domain

Godot removed VisualScript in 4.0, and published the number: 0.5% of the user base used it as their main language, from a poll of over 5,000. Their two stated reasons are worth reading against Raw. Users who tried it found the text language approachable enough that they preferred it. And "engines like Unreal, Game Maker or Construct offer high level game features packaged together with the visual scripting solution" — Godot's general-purpose node set gave visual scripting nothing to be good at.

The part they kept is the part that matters here: "Visual shaders are working well and appreciated by many users, so they're not going anywhere." Domain-specific node graphs win; general-purpose ones lose to text. Raw's defence is that its domain — a space, a scene, a page, an audience's device, a live input — is genuinely one a graph is the right notation for. The failure mode is drifting into a graphical rendering of an imperative program.

Store the graph as diffable text

This is the one place di.iiii is already ahead of every system surveyed, and it is worth knowing why. Max's .maxpat is JSON that reorders on save; the two community diff tools both concede that merging is impossible and one is described by its author as "ridiculously brute force." Pure Data references connections by creation index, so git can textually merge two patches into a file whose wires now point at the wrong objects — a silently, semantically wrong merge. Isadora has no text representation at all. Unreal's .uasset is binary and the sanctioned workflow is exclusive file locking.

di.iiii has UUID node identity, edges by UUID, an append-only op-log with inverses, and real-time multiplayer. That is the structural advantage, and it is already built.

Part six

One path, in order. The order is the recommendation.

The plan file already in the repo, docs/architecture/RAW_WORKSPACE.md, calls step 5.1 "the keystone" and says "do this first or every later node invents its own convention." It was not built, and two nodes — the keeper and MIDI in — were built on the ad-hoc liveOutputs Map anyway. That debt compounds with every node added.

  1. Build the port contract and a real clock

    Nothing else is worth starting first. A provider registration with per-port status (idle | starting | live | denied | unavailable | error), a scheduler that is not React's render, per-node state that survives a frame, and a declared volatility flag so caching stays correct.

    Take Wire's three flow types while defining it — signal, event, attribute — and make recompile cheap immediately. Take Isadora's two-axis port geometry so the CPU/GPU and live/static distinctions are visible rather than discovered at 6 fps.

  2. One code node, whose ports come from its source

    Not a text box on every node — values.__code is that idea and it has been inert since it shipped. One node type, body in QuickJS, ports parsed out of a declaration header with a stable short id separate from the display name.

    Bind the source at an attribute-flow port so editing it is structural, not per-frame. Precompile once, call many. Keep the port payloads primitive. Write the reconciliation — match by id, preserve wires and values, orphan removed inputs visibly — before the feature, not after the first complaint.

  3. Port promotion, so a subgraph becomes a node

    Every prior-art system makes the author declare which interior ports surface on the container. Notch's version is the one to copy: exposing a property hides all the others, so the abstraction is enforced rather than offered.

    Ship both kinds — a callable one with a signature, and an inlined one that can have multiple exits and contain suspending nodes. Then templates[] finally has a consumer and node.null finally has a purpose.

  4. Let Raw emit the ops it already has

    setPresentationState, setPublishState, upsertAsset. This is the "manage code and pages" complaint, and it is the cheapest item on the list — the ops, their inverses, the sync and the undo all exist.

    Fix /<space>/raw pointing at the scratch pad in the same change; it is a one-line routing bug that sends every new visitor to the wrong place.

  5. Automation is the same graph on a different clock

    The webhook receiver, the signed-decision channel, the deferred-action store with execution-time re-authorization — all shipped. What is missing is a registrable executor and a trigger node.

    The open question the plan file already recorded stays open and must be answered first: "whose credentials, and what the agent is allowed to touch." The feat/raw-admin rule is the right shape for it — no admin node declares an input port, ever, because an admin surface reachable from graph evaluation is a delete wired to a signal.

    For the execution side, measured: node:vm's timeout only covers synchronous execution. Five lines with a 200 ms timeout returned in 1 ms with no error, kept a microtask chain running on the host event loop, and OOM-killed the whole process 75 seconds later. isolated-vm stopped the identical case at 601 ms — separate heap, separate microtask queue — at ~1 MB and ~1 ms per sandbox, 2–5 µs warm, with prebuilt binaries so no compiler is needed on the VPS. The alternative with a boundary you can explain to an auditor is a deno run --deny-all subprocess per job at 4 ms, taking CPU and memory limits from systemd. And vm2 is not an option: revived in October 2025, 31 advisories in 2026, five of them CVSS 10.0, including a bypass of a 2023 patch.

What not to build

  • A bespoke code editor. CodeMirror 6. Darklang's 50% is the price of the alternative.
  • Graph → source transpilation. Epic shipped it for five versions and deleted it.
  • A projectional or structured editor. Same source, same verdict.
  • NDI, OSC, or arbitrary local processes in a tab. The plan file is right: this is the sandbox, not a gap. The gated stream.* and device.osc.* nodes are telling the truth.
  • A timeline editor, a DAW, a video mixer, projection mapping. Already refused in the plan; cutlab exists and is destined to live inside di.iiii. Compose, don't absorb.
  • A second parallel styling system. Admin and management surfaces reuse preferences-*.
  • A shader system from scratch. TSL already is one, in the stack, targeting both WebGL and WebGPU.
  • A node-graph library dependency, without reading its licence file. Rete's nesting plugin, rete-scopes-plugin, is CC-BY-NC-SA — non-commercial; the living, most-exercised litegraph now lives inside a GPL-3.0 frontend. Baklava is the only MIT option carrying typed sockets, registered type conversions and real subgraphs — and Raw's own graph already works, so this is a question about the evaluator, not the canvas.

What was actually looked at

Signed into prod and opened /raw seeded with the all-nodes example, at 1440×900: 40 nodes on screen, the ⋯ menu offering exactly Home / All Nodes Example / Streaming Prototype / Reset Workspace, and no code affordance anywhere in the DOM. Double-clicking a node enters it (breadcrumb ◈ › Multiply) onto an empty interior. Roughly 20k lines read across src/raw, src/project/graph, src/shared, src/studio and serverXR/src.

Gaps in this audit — stated rather than papered over

  • Raw has not been seen on a phone this session, and the command palette would not open under headless automation, so its contents are unverified. The plan file's open question #4 — "Does this workspace need to work on a phone?" — is still open.
  • Three automation platforms were briefed and never read: n8n, Node-RED and Windmill. Windmill is the closest shipped thing to "code and low-code in one workspace" and should be read before step 5 is designed. ComfyUI was covered — its lazy inputs and its node-expansion mechanism, where a node returns a subgraph to run in its place with per-node cache granularity, are the two ideas worth stealing from that corner.
  • Blender's section was built from its C++ headers rather than its manual, because docs.blender.org and devtalk.blender.org both refuse automated requests. Better for design questions, but it means no user-complaint colour on the field system — and fields are the part users reportedly struggle with.
  • Epic's own wording on why Blueprint nativization was removed could not be retrieved — their docs render client-side. The removal is certain; the stated reasons are not sourced here.
  • Figma has published nothing naming their engine since 2019; current QuickJS use is inferred from third-party reports and the absence of any announcement.

In-flight work this must not collide with

PR #121 (the plan, keeper, MIDI in, zen) and PR #100 (timeline core) are merged, not open — the memory index saying otherwise is stale. Two PRs are genuinely open: #99 and #119. #99 is 157 commits behind dev with 11 conflicts and its substance already landed by another route — but its unreviewed WIP commit contains work.status and work.agent node types plus agentRunRoutes.js and workStatusRoutes.js, which is a prototype of step 5 and should be read before that step, not merged. feat/raw-admin is one clean commit with no PR yet.
